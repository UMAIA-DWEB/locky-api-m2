### 3.1.3 Autenticação e Autorização (OAuth 2.0)

#### O que é o OAuth 2.0

O OAuth 2.0 permite que uma aplicação (cliente) tenha acesso a dados de um utilizador noutro servidor sem precisar das credenciais. Em vez disso, o servidor que conhece o utilizador (neste caso, o GitHub) emite tokens de acesso.

Nesta API:

- Cliente: a LockyAPI
- Utilizador: a pessoa com conta GitHub
- Servidor de autorização e de recurso: o GitHub
- O que peço: o perfil público (username, email)

#### Os quatro flows do OAuth 2.0

A especificação define quatro flows. Aqui ficam todos com uma frase cada e o porquê de só um servir:

| Flow | Quando se usa | Razão |
| --- | --- | --- |
| **Authorization Code** | Apps com backend | É exatamente este o caso. Foi este que escolhi. |
| **Implicit** | SPAs antigas, sem backend | Deprecated em OAuth 2.1. Tem o token no URL, o que tem riscos. |
| **Client Credentials** | Comunicação máquina-a-máquina, sem utilizador | Não serve, porque aqui há sempre um utilizador. |
| **Resource Owner Password** | Casos legados em que o cliente é totalmente de confiança | Vai contra o objetivo do OAuth (o cliente nunca devia ver a password). Removido em OAuth 2.1. |

O *Authorization Code* funciona assim: a aplicação manda o utilizador para o GitHub, ele autoriza, e o GitHub devolve um código curto. Depois o servidor troca esse código por um access token numa chamada que vai diretamente do servidor para o GitHub. O token nunca passa pelo browser do utilizador, o que é a principal vantagem de segurança.

#### Implementação no projeto

A estratégia do Passport está em `src/config/passport.js`. Uso o `findOrCreate` para evitar duplicar utilizadores quando alguém faz login várias vezes. Só pedi o scope `user:email`.

Em vez de mandar o token em cada pedido, criei uma sessão HTTP com o `express-session`. O servidor guarda o id do utilizador na sessão e o browser fica com um cookie `connect.sid`. Em cada pedido seguinte, o Passport vai à BD buscar o utilizador outra vez e mete-o em `req.user`.

#### Camadas de autorização

Implementei dois middlewares:

- **`isAuthenticated`** - devolve 401 se não houver sessão.
- **`isOwner`** - vai buscar a reserva pelo id e compara o `userId` com o utilizador da sessão. Se não for o dono, devolve 403.

Na rota usam-se os dois em sequência:

```js
router.put('/:id', isAuthenticated, isOwner, ctrl.update);
```

A ordem importa: quem não está logado é parado logo no `isAuthenticated` e recebe 401. Quem está logado mas não é o dono é parado no `isOwner` e recebe 403. Os dois códigos são diferentes de propósito: 401 é "não sei quem és", 403 é "sei quem és mas não podes".

#### Acesso aos próprios recursos

Para que cada utilizador veja apenas as suas reservas, fiz duas coisas:

1. No GET por id (`/api/reservations/:id`), o `isOwner` bloqueia se a reserva não for sua.
2. Na lista (`/api/reservations`), o controller adiciona `where: { userId: req.user.id }` à query SQL, e portanto as reservas dos outros nem chegam ao processo Node.

### 3.1.4 Documentação Interativa

Para a documentação OpenAPI 3.0 usei a biblioteca `swagger-jsdoc`. A spec vive em `src/docs/swagger.js` e é servida em `http://localhost:3001/api/docs` via `swagger-ui-express`. Tem as 4 secções (Auth, Stations, Lockers, Reservations), os schemas das entidades, e funcionalidade *Try it out*.

A *collection* Postman (`postman/LockyAPI.postman_collection.json`) tem os 19 endpoints organizados em quatro pastas, com exemplos de body para os POST/PUT. A descrição da collection explica como configurar a autenticação por cookie - passo necessário porque o flow OAuth 2.0 *Authorization Code* não é executável diretamente no Postman (requer redirects browser <-> GitHub).

### 3.1.5 Containerização

A aplicação corre como dois serviços orquestrados por Docker Compose:

- **`db`** - `mysql:8.0` com volume persistente e *healthcheck*. Porta `3307` no host (mapeada para 3306 no container) para evitar conflito com instalações locais de MySQL;
- **`app`** - Node 20 alpine, porta `3001` no host (3000 no container), depende de `db: service_healthy`.

Variáveis sensíveis (passwords, OAuth secrets) ficam no `.env`, excluído do Git.

## 3.2 Instalação

### Pré-requisitos
- Docker Desktop
- Conta GitHub (para criar a OAuth App)

### Passos

É preciso Docker Desktop aberto e uma OAuth App registada no GitHub. O passo a passo está no [c3](./doc/c3.md#32-instalação).

1. Clonar este repositório;
2. Criar um ficheiro `.env` na raíz com esta estrutura:

```bash
DB_HOST=db
DB_PORT=3306
DB_NAME=lockyapi
DB_USER=locky
DB_PASSWORD=lockypass
DB_ROOT_PASSWORD=rootpass

PORT=3000
NODE_ENV=development

SESSION_SECRET=top-secret-session-key

GITHUB_CLIENT_ID=[ir ao github buscar]
GITHUB_CLIENT_SECRET=[ir ao github buscar]
GITHUB_CALLBACK_URL=http://localhost:3001/auth/github/callback
```

3. Editar o Client ID e Client Secret com os nossos valores (Github -> OAuth Apps)
4. Arrancar:

```bash
docker compose up --build
```

Disponível em `http://localhost:3001`.

5. Popular a BD (num terminal separado)

```bash
docker compose exec app npm run seed
```

## 3.3 Usage

Pontos de entrada principais:

- `http://localhost:3001/api/docs` - documentação Swagger UI
- `http://localhost:3001/auth/github` - login OAuth (abrir no browser)
- `http://localhost:3001/api/stations` - endpoint público
- Importar `postman/LockyAPI.postman_collection.json` no Postman para testar todos os endpoints

**IMPORTANTE**: Como configurar autenticação no Postman:
- fazer login no browser, copiar o cookie `connect.sid` (DevTools -> Application -> Cookies), e colar no Cookie Manager do Postman para o domínio `localhost`. Os pedidos passam a ser enviados autenticados.

## 3.4 Notas

- O *seeder* (`src/seeders/seed.js`) foi gerado com auxílio de uma ferramenta de IA: as 30 estações portuguesas (nomes e moradas) e o padrão de geração dos 90 cacifos e 30 reservas vieram de uma sugestão da IA, que depois revi e ajustei. O resto do código é autoria própria.
- O `MemoryStore` por defeito do `express-session` perde sessões em cada reinício do container. Em produção usaria um store externo (Redis ou tabela na BD). Para este projeto académico é aceitável.
